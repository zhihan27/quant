# 2026-10-16 模型治理：最终留出集 · 通过率监控 · 漂移监控 · 告警降级

需求来源：`xuqiu.txt`（六个模块，A 最终留出集 / B 通过率监控 / C 漂移监控 / D 告警与降级 / E 管理员页面 / F 测试）

## 一、需求澄清（动工前与用户确认的五项）

| 议题 | 用户选择 | 落地方式 |
| --- | --- | --- |
| 留出集口径 | **评估专用模式** | 留出集只约束 `evaluate_final_holdout` 那一次：评估用的冻结模型只用 `< FINAL_HOLDOUT_START` 的数据训练。日常生产 `train_market_context` 保持现状，按滚动窗口用全量历史重训。**这是对需求文 A-2「任何训练都不能用留出集数据」的有意偏离**，理由见下 |
| 回滚机制 | **归档目录 + 注册表** | `models/archive/` 存通过版本的 joblib + json 摘要；`quant_model_registry` 登记 context_id / passed / archive_path / is_active；回滚 = 归档文件原子替换回活动路径 |
| 写入时机 | **随扫描同批写入** | 在同一次 `compute_lock` 内、训练结束后写通过率与漂移，不新增定时任务 |
| 估值维度 | **如实标注未接入** | 行情源未提供 PE/PB，估值漂移列为显式占位条目并写明原因，不补采、不拿别的列冒充 |
| 降级动作 | **自动降级，回滚需确认** | 自动：标 degraded + 暂停评分 + 写告警；需管理员点击：解除降级、回滚、重训，均写审计 |

### 偏离理由（留出集「评估专用」）

需求文 A-2 要求任何训练都不能使用留出集数据。严格执行的代价是：`FINAL_HOLDOUT_START` 之前的可训练历史只有约 530 个交易日（本地逐股日线按 `count=1200` 采集，实测区间 2021-11-03 → 2026-10-16），**小于系统配置的 750 日滚动窗口**，日常生产模型将被迫长期丢掉近端样本、与留出集评估的那一份不是同一个模型，结论也就无法代表线上模型。因此选择「评估专用」：留出集对**被评估的那一次训练**严格不可见（冻结模型只喂留出集起点之前的数据），日常生产训练不受约束。这个偏离写在 `services/model_governance.py` 顶部与 `README.md` 的页面六说明里，不在代码注释之外悄悄生效。

## 六、排障轨迹

本轮共发现 5 个缺陷，其中**第 5 个是生产环境的静默失效**。

### 6.1 `sql/005` 用了保留字 `window`，整份迁移从未成功应用

`concept_drift` 表照着需求文原样写了列名 `window`，而 `window` 是 PostgreSQL 的保留字，`CREATE TABLE` 直接语法报错。因为迁移是整份执行、首条语句即失败，**真实库 `quant_schema_versions` 当时只到 4**，治理相关的九张表一张都不存在，而失败只体现在启动日志里。修复：列名改为 `window_days`，把原因写进 SQL 注释（`sql/005_model_governance.sql:104-106` 与 125 行的 `COMMENT ON COLUMN`），并新增隔离模式下的建表用例。

### 6.2 测试替身漏了 `cursor()`，批量写入逃逸到真实 `public` 模式

`_ScopedConnection` 最初只替换了 `execute()` 的 schema，而 `log_validation` 的一批记录走的是 `cursor().executemany()`——**写入落到真实的 `public` 模式**，读取却走测试模式。测试于是「通过」或「查无数据」，实际污染了主库。修复：补 `_ScopedCursor`（提供 `execute` / `executemany` / `__enter__` / `__exit__`），`cursor()` 返回它。这条已写进 `tests/test_model_monitor.py` 的类注释，避免后来者再踩。

### 6.3 用例之间数据累积导致的误判

类级 schema 复用、逐用例不清理时，追加写入的检验记录会被下一条用例一起数进去，通过率与连续失败的断言随之漂移。修复：`setUp` 里 `TRUNCATE` 相关表。

### 6.4 `prediction_drift_row` 只认整数周期键，会谎报「没有通过验证的模型」

上下文里的 `models` 字典在落盘/回传后会变成 JSON 形状（键为字符串 `"20"`），而取预测漂移的代码只按整数 `20` 查找，取不到就当成「本轮没有通过验证的模型」——一个看起来正常的空结论，而非报错。修复：两种键都认，并把用例加强为断言 `prediction["stocks"] == settings.DRIFT_PREDICTION_TOP_N` 且 `industry_hhi` 非空，只有修好的版本才过得去。

### 6.5 `fetch_failure_streaks` 外层 SELECT 漏掉 `position`，通过率告警在生产环境从未生效

`services/model_monitor.py::fetch_failure_streaks` 的内层算出了 `row_number() ... AS position`，外层 `SELECT` 却只取了 `model_type, target_type, pass, failed_gate, scan_time`。判定函数 `evaluate_pass_rate_alerts` 按 `item["position"]` 排序，于是**只要库里有一条检验记录就 `KeyError: 'position'`**。而 `ScanGovernance.after_scan` 只在 `check_pass_rate_alerts` 外面兜了 `DatabaseError`，KeyError 一路逃到 `scan_pipeline` 的 `except Exception`，被记成一句「模型治理未完成：KeyError: 'position'」——**症状是一句页面提示，而不是失败**，所以通过率告警（连续失败 / 月度通过率 / 单门槛失败率）从来没有真正触发过。

修复：

```python
# position 必须出现在外层 SELECT 里：判定函数按它取「最近 limit 次」，
# 漏掉这一列会让连续失败告警在有任何一条检验记录时直接 KeyError。
"SELECT model_type, target_type, pass, failed_gate, scan_time, position FROM ("
```

并补了一条针对性回归用例：

```python
def test_failure_streaks_expose_the_position_the_judgement_reads(self):
    """判定函数按 ``position`` 取「最近 N 次」。取数 SQL 漏掉这一列时，
    只要有任意一条检验记录，连续失败告警就会 KeyError——
    而它被扫描管线兜住，表现为页面上一句「模型治理未完成」，通过率告警悄悄失效。"""
```

根因与本轮 `sql/005` 的保留字问题是同一类：**新写的数据库路径在真实库上跑通之前，没有一条用例真正压过它**。

### 6.6 构造指标少一个键，把「通过」判成了「不通过」

`test_scan_writes_all_three_drift_tables_and_the_validation_log` 一度断言 `0.0 != 0.5`：构造的样本外指标漏了 `universe_excess_return`，Top 超额门槛比的是「相对股票池均值」的超额，缺这一项直接判不通过，于是本该 50% 的通过率成了 0%。修复：补齐 `universe_excess_return` / `mae` / `baseline_mae` / `score_kind`，并把原因写进用例注释——**这是替身没跟上门槛口径，不是门槛有问题**。

## 七、遗留与需要确认

2. **真实数据下的证据缺失**：见 §5.6，治理表当前 0 行。
3. **估值维度未接入**：`quant_feature_drift` 里以带原因的占位条目呈现（`note` 写明「行情源未提供 PE/PB」），不参与告警判定。
4. **`tests/test_auth.py:281`**：见 §6.7，需要确认是删除该断言还是恢复页面文案。

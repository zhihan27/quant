## 1. 为什么要收敛扫描权限

扫描训练出的是一份**全局共享**的模型上下文（`models/market_context_v2.1.0.joblib` + `data/ml_panel_v2.1.0.parquet`），所有账号的「个股分析」都读它。这带来两个后果：

1. **谁扫谁就决定别人看到什么。** 任何一个人扫一次，就把别人刚建好的截面覆盖掉；股票池小的时候（有人只扫 30 只自定义代码），整个系统当天的模型就退化成 30 只股票的截面——这正是用户此前反复看到「当前股票不在已训练截面内，或日线已更新，请重新扫描股票池」的根因。
2. **没有稳定的一天一版。** 模型只在有人点按钮时才更新，收盘后没人点，第二天大家用的还是前一天的截面。

目标形态：**扫描权收归管理员，结果对所有账号只读开放。** 页面按角色分支而不是按路由注册——`tests/test_auth.py` 的 `BUSINESS_PAGES` 保持不变，量化选股页仍在导航里，只是非管理员看不到筛选表单与「开始扫描」按钮。

## 2. 抽离无界面编排：`services/scan_pipeline.py`

定时任务要在没有网页的进程里跑同一套流程。若在别处再抄一份编排，两边迟早各改一半——本仓库刚因为「创业板 302 号段」在 10 处各写一份而翻过车（见 `test_records/2026-10-16_创业板302号段漏登记与个股分析页界面修复.md`）。因此把 `pages/2_量化选股.py` 里内联的约 195 行编排抽成无界面服务层，页面退化成收集输入、渲染输出的薄壳。

抽离时把两处**隐式契约显式化**：

**(a) 一条靠代码恰好写对才成立的顺序依赖。** 组合回测要用扫描期间收集的逐股 `history`，而 `item.pop("history", None)` 会把它释放掉以省内存。原页面能跑只是因为顺序恰好对。搬进服务层后写成结构并由单测钉住：

```python
    if options.run_portfolio and context:
        ...  # 组合回测在逐股评分循环之前跑完

    for item in ready:
        ...  # 逐股评分

    # 到这里组合回测与逐股评分都已用完 history，可以释放扫描期间收集的逐股历史。
    for item in ready:
        item.pop("history", None)
```

**(b) 进度回调的两种调用约定。** `train_market_context` 与 `run_portfolio_strategy` 的 `progress` 只吃一个 `message`；页面的 `task.step` 是三参数的 `(message, completed, total)`。页面直接传 `task.step` 能工作，靠的是后两个参数有默认值。服务层接口统一按三参数定义，并用一个适配器把这个巧合显式化：

```python
def _message_only(progress: ProgressCallback | None) -> Callable[[str], None] | None:
    """把三参数进度回调适配成子服务需要的单参数回调。"""
```

页面上原本 8 处承载**数据血缘信息**的 `st.caption`/`st.info`/`st.warning`（暴露数据状态、因子并入结果、上下文限制说明）没有丢，改成结构化的 `result.notes` 返回给页面按 level 渲染；同时用 `objective_label()` 包了一层，避免把 `lambdarank` 这样的内部标识直接显示给用户（沿用本仓库「结果展示白话化」的口径）。

`ScanOptions.pool_mode` 做了一次校验，因为 `services/scanning.py:55` 是 `{"沪深主板": "main", ...}.get(mode, "all")`——**写错一个标签会静默退化成全市场扫描而不是报错**：

```python
    def __post_init__(self) -> None:
        if self.pool_mode not in POOL_MODES:
            raise ValueError(f"未知的股票范围 {self.pool_mode!r}；可选：{'、'.join(POOL_MODES)}")
```

## 3. 并发锁漏洞

### 3.1 原来的写法

```python
heavy = title in {"个股分析", "扫描与模型分析", "滚动样本外回测", "配对统计分析"}
```

`pages/2_量化选股.py:283` 的「Top-N 组合构建与摩擦成本回测」**不在这个集合里**，因此完全没有并发保护。任何人改动标题文案（哪怕只是加个空格）都会让对应的锁静默失效。

### 3.2 拆成两层

`services/workload.py` 拆成纯 Python 的 `compute_lock()` 与 Streamlit 包装 `compute_slot()`，后者只负责捕获异常并渲染提示：

```python
class ComputeBusy(RuntimeError):
    """计算槽位被占用，异常消息即面向用户的提示语。"""

@contextmanager
def compute_lock(repository=None) -> Iterator[None]:
    """不依赖 Streamlit 的跨进程计算锁，繁忙时抛出 ComputeBusy 而不排队。"""
```

**`ComputeBusy` 携带面向用户的确切消息**，`compute_slot` 只做 `st.warning(str(exc))`。初稿写的是按 `exc.args[0].startswith("已有")` 挑措辞——那正是刚从 `ui_helpers` 移除的同一类隐式契约缺陷，已否决。

`loading_task` 改成调用方显式声明：

```python
def loading_task(title, detail="...", *, exclusive: bool = False) -> Iterator[LoadingTask]:
```

8 个调用点的归属：

| 位置 | 环节 | exclusive |
| --- | --- | --- |
| `pages/1_个股分析.py:87` | 刷新/查询股票目录 | False |
| `pages/1_个股分析.py:138` | 个股分析 | **False（本次改）** |
| `pages/1_个股分析.py:381` | 滚动样本外回测 | True |
| `pages/1_个股分析.py:457` | 配对统计分析 | True |
| `pages/2_量化选股.py` | 获取完整股票池 | False |
| `pages/2_量化选股.py` | 扫描与模型分析 | True |
| `pages/3_自选与持仓.py:140` | 刷新持仓报价 | False |
| ~~`pages/2_量化选股.py:283`~~ | ~~Top-N 组合构建~~ | 该环节并入 §2 的服务层，调用点消失 |

### 3.3 个股分析移出锁的依据（核实过，非假设）

它只读已落盘的模型、只算一只股票、不写任何共享产物：

| 共享资源 | 并发安全性 | 依据 |
| --- | --- | --- |
| SQLite 缓存 | 一写多读 | `timeout=10` + `PRAGMA journal_mode=WAL`，`services/market_data.py:132-133` |
| Parquet 面板 | 原子替换 | 临时文件 + `os.replace`，不会读到半个文件 |
| 模型 joblib | 只读 | 个股分析不训练，`train_market_context` 只在扫描里调用 |

最坏情况是某一方少一次缓存命中或多等几秒，不会脏读。

### 3.4 锁编号必须共用

```python
# 跨进程计算互斥：同一数据库同时只允许一个重计算任务（扫描、组合回测、滚动重训）。
# 网页端与每日定时扫描进程必须共用这一个编号——两者写的是同一份
# models/market_context_v{MODEL_VERSION}.joblib 与 data/ml_panel_v{MODEL_VERSION}.parquet，
# 各自另起一个编号等于放弃互斥，两边会同时训练并互相覆盖，
# 而 load_context(include_panel=True) 靠 context_id 比对，读到的模型与面板会来自不同批次。
COMPUTE_LOCK_KEY = 706821026
```

探查阶段曾建议给定时任务用新编号 `706821027` 以避开与网页端手动扫描的竞争——**已否决**，理由写在常量上方。`tests/test_workload.py::test_lock_uses_the_shared_configuration_key` 把「实际传入的编号就是 `settings.COMPUTE_LOCK_KEY`」钉住，`test_compute_lock_key_does_not_collide_with_other_locks` 挡住与建表锁 706821024 / 监控锁 706821025 撞号。

## 4. 定时任务：`scan_daily.py`

三道判定按顺序生效，命中前两条时**不训练、不落盘**并以退出码 0 结束：

**(1) 数据就绪（本次最关键的保护）。** 收盘后行情源的当日 K 线尚未更新时，逐股采集会把整池判成「历史行情未更新至报价对应的完整交易日」而大批排除，训练出一个几乎是空截面的模型，然后**静默覆盖掉原本可用的好模型**——全程没有任何报错。因此宁可什么都不做：

```python
    latest = str(pd.Timestamp(history["date"].iloc[-1]).date())
    if latest != _today():
        return f"当日 K 线尚未更新（沪深 300 已完成日线最新为 {latest}，今天是 {_today()}）"
```

**(2) 幂等。** 已落盘上下文的 `reference_date` 已经是今天就不再重复训练。周末与节假日靠这条自然覆盖，**不需要维护交易日历**。

**(3) 计算锁。** `compute_lock()` 繁忙时记日志并退出码 1，不排队。

另加一条：扫描跑完但**一行候选都没有**时不落盘，免得把只读视图上原本可看的排名换成一张空表。

命令行：`--force`（跳过前两道判定）、`--dry-run`（只打印参数与跳过原因，不联网、不落盘）。退出码 0 = 成功或按判定正常跳过，1 = 失败需查 `logs/daily_scan.log`。

日志照 `services/market_data.py:102-110` 的属性标记幂等写法挂 `RotatingFileHandler`，同时输出 stdout 供 `journalctl` / 计划任务查看。

## 6. 排障轨迹

| 现象 | 判断 | 证据 | 结论 |
| --- | --- | --- | --- |
| 反证脚本报「还原失败，文件内容与还原前不一致」 | 以为还原逻辑写错了 | `git diff` 只显示预期的 11/4 行；`git ls-files --eol` 显示工作区由 `w/lf` 变成 `w/crlf` | **误报**。`Path.write_text` 在 Windows 上翻译换行符，不是还原失败 |
| `loading_task` 在裸环境下抛 `StreamlitAPIException: update() is not a valid Streamlit command` | 以为新实现有 bug | 异常发生在 `_loading_display` 的 `st.status(...).update()`，与并发判定无关 | **用例写法问题**。该用例只问「有没有加锁」，改为 patch `_loading_display` |
